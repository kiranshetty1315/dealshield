# DealShield AI — API Contracts & Specifications

This document defines the canonical API contracts for DealShield AI. The FastAPI backend serves as the **single source of truth** for all request and response schemas, automatically generating an interactive OpenAPI 3.1 specification at `/openapi.json` and `/docs`.

---

## 1. API Versioning Convention

All domain endpoints are strictly versioned under `/api/v1/`:
- Root Health Probes: `GET /health` and `GET /api/v1/health`
- Chat Ingestion: `/api/v1/chats/*`
- Structured Analysis: `/api/v1/analysis/*`
- Agreement Lifecycle: `/api/v1/agreements/*`
- Confirmations: `/api/v1/confirmations/*`
- Evidence Vault: `/api/v1/evidence/*`

Any breaking schema changes will require a major version increment to `/api/v2/`.

---

## 2. Shared Agreement Analysis Schema

The central contract of DealShield AI is the **Agreement Analysis**, which transforms an informal multi-party conversation into verified commercial terms, explicit contradictions, and missing statutory safeguards.

### Core Structure Fields

| Field | Type | Description |
|---|---|---|
| `analysis_id` | String (UUID) | Unique analysis record identifier |
| `chat_id` | String | Reference to source conversation |
| `parties` | Array[Party] | Identified contracting entities with roles |
| `extracted_terms` | Array[ExtractedTerm] | Agreed, proposed, or contested terms |
| `conflicts` | Array[ConflictItem] | Disagreements and ambiguous acceptances |
| `missing_terms` | Array[MissingTerm] | Commercial/statutory provisions missing from chat |
| `confidence_score` | Float (0.0 to 1.0) | Model confidence in extraction accuracy |
| `requires_human_review` | Boolean | Flags when ambiguity or price variance requires user action |
| `analyzed_at` | ISO 8601 Timestamp | Processing timestamp |

### Message Citation Model
Every extracted term and conflict includes `source_message_ids: string[]`. These reference stable deterministic message IDs generated by the chat parser (e.g. `msg_raj_003_a1c2e4`), enabling the frontend to highlight the exact chat bubbles that substantiate any clause.

## 3. Endpoints & Payloads

### `POST /api/v1/chats/upload`
Ingests a WhatsApp `.txt` export file or raw text.

**Request:** `multipart/form-data` with `file: UploadFile` OR `text/plain` body.

**Response (201 Created):**
```json
{
  "chat_id": "chat_a9d3e8b712c4",
  "filename": "sample-negotiation-01.txt",
  "party_names": ["Raj Mehta", "Priya Sharma"],
  "message_count": 10,
  "status": "parsed",
  "messages": [
    {
      "message_id": "msg_rajmehta_000_c528f1",
      "sender": "Raj Mehta",
      "content": "Hi Priya, regarding the website project we discussed",
      "timestamp": "2024-03-12T10:15:00Z",
      "sequence_number": 0,
      "raw_line": "12/03/24, 10:15 - Raj Mehta: Hi Priya, regarding the website project we discussed"
    }
  ]
}
```

### `POST /api/v1/evidence/verify`
Verifies SHA-256 fingerprint consistency.

**Request:**
```json
{
  "content": "Agreement text here...",
  "expected_hash": "a1b2c3...64chars"
}
```

**Response:**
```json
{
  "is_valid": true,
  "computed_hash": "a1b2c3...64chars",
  "expected_hash": "a1b2c3...64chars",
  "explanation": "Content matches the recorded SHA-256 fingerprint exactly. Integrity verified.",
  "limitations_notice": "SHA-256 verifies that content has not been tampered with since hashed. It does NOT independently prove identity, execution, or legal electronic signature under Indian law."
}
```

## 4. Frontend TypeScript Type Generation Workflow

Frontend engineers should **never write duplicate manual schemas**. When backend Pydantic models change:

```bash
# 1. Ensure backend is running locally
uvicorn app.main:app --port 8000

# 2. In apps/web, run openapi-typescript
cd apps/web
npx openapi-typescript http://localhost:8000/openapi.json -o src/types/api-generated.ts
```
